# K-BOX 视频系列主题体系 · 讨论稿

日期：2026-11-01。目标：覆盖客户、售前、使用者、实施、开发者、架构师与运维；先形成完整体系，再按业务价值滚动制作。

本稿依据工作区当前产品文档、设计总览、菜单配置与关键源码静态核对编写。既有试片已覆盖六个公开产品页面。候选主题不表示已完成线上功能验收；新入口与细节必须以录制环境实测为准。

## 内容设计判断

主线：业务问题 → 知识接入 → 知识组织与治理 → 检索/阅读/推理/问数 → 可信供给 → 效果与权限验收。

区分四种视频：认知与选型（3–6 分钟）、任务实操（5–10 分钟）、原理与参数专题（3–7 分钟）、效果诊断与方法（4–8 分钟）。每条只解决一个核心问题，附前置条件、示例资料、验证结果、适用版本与来源文档。

四类对外价值表达（RAG、Wiki、图谱、数据洞察）不等于内部只有四种容器。QA 和术语库值得独立教学；数据主题也不是知识空间下的一种文档库。

## 统一案例与制作规范

- 贯穿案例一：企业制度与员工服务。材料包括制度正文、一个过期版本、FAQ、部门标签与不同访问角色。用于文档、QA、Wiki、权限、更新与检索。
- 贯穿案例二：产品—供应商—资质。使用少量跨文档关系与可明确核对的原始证据，用于图谱和本体。
- 贯穿案例三：订单—客户—回款。采用合成数据，包含一对多关系、明确时间和指标口径，用于数据洞察、SQL 核验及 Query Memory。
- 每个案例保留正常题、无答案题、权限题、过期或冲突题。图谱/问数另设关系与统计粒度错误题。
- 首条先展示完成结果，再说明前提，执行操作，最后验证结果并链接后续专题。慢任务可剪辑等待时间，并明确标注。
- 公开课程和内部研发课分开标记；参数、内部故障与技术设计按受众进入，不混入所有用户的首课。
- 保存讲稿、字幕、配音、录屏分镜、样例数据和功能版本。UI 变动主要更新实操片段，概念片保持独立。

## 事实核对与录制边界

- 知识空间的主要职责是统一向量化方案；“每个部门建一个空间”不应成为默认教学模板。
- 后台管理权、资源协作权、内容消费权是不同维度；每种接口的身份和过滤规则必须分别验证。
- Wiki 自动生成与发布不代表业务权威审核；页面链接图与实体关系图是不同产物。
- 文档多轮检索已能处理部分跨文档问题；图谱的价值在于显式关系资产的长期管理和查询复用。
- 当前集成概述将飞书列为已上线，钉钉/企业微信列为规划；平台概述存在更宽泛表述，录制前应核对实际版本。
- MCP 不能被描述为覆盖所有资产的统一完整入口；以实际可发现工具为准。
- Skill 说明存在多代口径。当前源码枚举包括 DOC_KB、WIKI_KB、GRAPH_KB、DATA_INSIGHT、ONTOLOGY，最后一种为已发布本体的离线快照；不能统一讲成依赖 CLI，也不能承诺所有 Agent 平台无需适配。
- 数据洞察应用链路与外部 Skill 工具链有不同职责和执行校验边界；只读账号、SQL 检查与业务口径验证需要分别说明。
- 文档有效期禁用不等同归档审批；模型用量看板不等同知识回答质量评测。工作区另有知识库储量统计页面，也不应误称平台毫无统计。
- 信息提取、本体中心与建库模板等在当前工作区可见，不能据此断言网站部署已同步或具体流程已完成验收。
